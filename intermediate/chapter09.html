9-1 データ関連のトラブル

テーブル設定・カラム・リレーション・Virtual Column などで発生しがちなトラブルと対処法をまとめます。

🔴 社員ID の Ref ドロップダウンに候補が出ない
💡 原因

カラムの Type が Ref になっていない／Source table が正しくない／参照先テーブル（社員マスタ）にデータがない、のいずれかです。

✅ 対処法
1

Data → 勤怠記録（または休暇申請）→ 対象カラム（社員ID）の Type を Ref に変更します。

2

その下の Source table に「社員マスタ」を指定します。

3

社員マスタに最低1行以上データが入っているか確認します。

4

エディタ右上の Save → Sync を実行します。

🔴 Virtual Column の式でエラーが表示される（ #REF! など）
💡 原因

参照しているカラム名のタイプミス／参照先 Virtual Column がまだ定義されていない／計算型と実際のデータ型が一致しない、などが考えられます。

✅ 対処法
1

Data → Columns で、該当の Virtual Column の App formula を開きます。

2

式内のカラム名を再確認します（全角スペース・余分なカッコ・誤字に注意）。AppSheet はカラム名を [ ] で囲む必要があります。

3

他の Virtual Column を参照している場合、参照先が先に定義されている ことを確認します。例：「勤務ステータス」は「勤務時間」を参照するため、勤務時間が先に定義されている必要があります。

4

式の右側にある Test ボタンで実値をテストし、エラーメッセージを確認します。

🔴 日付・時刻のカラムが意図しない形式で表示される
💡 原因

スプレッドシート側のセル書式と AppSheet 側の Type が一致していません。また、AppSheet の Data locale（ロケール設定）が日本になっていないと、日付順や時刻の12h/24h表記が変わります。

✅ 対処法
1

スプレッドシート側で「ファイル → 設定 → 全般 → 地域」が 日本 になっているか確認します。

2

AppSheet で Data → Tables → 対象テーブル → Localization → Data locale を Japan (ja-JP) に設定します。

3

カラムの Type が Date / Time / DateTime のいずれで、スプレッドシートの値と整合しているか確認します。

🔴 Initial Value を設定したのに、新規作成時に値が入らない
💡 原因

Initial Value は フォームで新規作成するタイミング にしか評価されません。スプレッドシートで直接追加した行や、Action の「Set these columns」で上書きした行には適用されません。

✅ 対処法
1

Data → Columns で、該当カラムの Initial value が正しく設定されているか確認します（例：申請日なら TODAY()）。

2

アプリの フォームから 新規作成して動作を確認します（スプレッドシート直接追加ではなく）。

3

Action を使って行を追加する場合は、Set these columns に同じカラムが含まれていないか 確認します。含まれていると Initial value より優先されます。

🔴 Sync してもスプレッドシートの変更が反映されない
💡 原因

AppSheet のキャッシュが残っている／ヘッダー行の列名が変わっていて整合が取れていない、などが原因です。

✅ 対処法
1

エディタ右上の Sync（🔄）ボタン をクリックします。

2

反映されない場合は、Data → Tables → 対象テーブル → Regenerate Structure を実行します。

Regenerate Structure を実行すると、カラム設定（Type、Label、Formula など）がリセットされる場合があります。実行前に重要な設定をメモしておきましょう。

9-2 ビュー・書式関連のトラブル

Slice・Format Rules・ビュー表示に関するトラブルをまとめます。

🔴 Slice に該当するレコードが表示されない
💡 原因

Row filter condition（絞り込み条件式）が意図通りに評価されていない、または条件が厳しすぎて該当レコードがない可能性があります。

✅ 対処法
1

Data → Slices で対象 Slice を開き、Row filter condition の式を確認します。

2

式の右側の Test ボタンで、各レコードでの評価結果を確認できます。TRUE になっているレコードが Slice に含まれます。

3

テスト用のレコードを1件スプレッドシートに追加して、該当する条件のデータを入れてから Sync します。

Enum カラムで絞り込む場合、比較文字列の 全角・半角 や 前後のスペース に注意してください。[承認ステータス] = "申請中" と [承認ステータス] = "申請中 "（末尾にスペース）は別物と判定されます。
🔴 Format Rule が適用されない
💡 原因

条件式が FALSE になっている／「Format these columns and actions」でカラムが選択されていない／他のルールと競合している、などが原因です。

✅ 対処法
1

Views → Format rules で対象ルールを開き、If this condition is true の式を Test します。

2

Format these columns and actions で、書式を適用したいカラムにチェックが入っているか確認します。

3

複数のルールが同じカラムを対象にしている場合は、後に作成されたルール（リストの下）が優先 されます。条件式を排他的になるように調整するか、ルールの適用順を意識してください。

🔴 Ref_Rows が inline で表示されない
💡 原因

親テーブルの詳細画面に子レコード一覧（Ref_Rows）が表示されない場合、子テーブル側の Ref 設定に 「Is a part of?」 の設定が不足していることが多いです。

✅ 対処法
1

子テーブル（勤怠記録 または 休暇申請）の Ref カラム（社員ID）を開きます。

2

Is a part of? を ON にするか、親テーブル（社員マスタ）のカラム一覧に Related 勤怠記録s のような Virtual Column が自動生成されているか確認します。

3

親側の詳細ビューで、その Related カラムが 非表示（SHOW? が FALSE） になっていないか確認します。

🔴 ビューのカラム順が意図した順にならない
💡 原因

ビューの Column order が未設定の場合、スプレッドシートの列順で表示されます。意図した並び順にするには明示的に設定する必要があります。

✅ 対処法
1

Views → 対象ビューを開き、View Options → Column order を展開します。

2

「+ Add」をクリックし、表示したい順番にカラムを1つずつ追加します。追加した順番がそのまま画面上の表示順になります。順番を変えたい場合は、一度削除してから正しい位置に追加し直してください。

9-3 Action・Automation 関連のトラブル

第7章・第8章で作成した Action と Bot に関するトラブルの対処法です。

🔴 Action のボタンが画面に表示されない
💡 原因

Only if this condition is true が常に FALSE になっている／Position が「Hide」になっている、などが考えられます。

✅ 対処法
1

Behavior → Actions で対象の Action を開き、Behavior セクションの条件式を確認します。Test で TRUE になるレコードがあるかチェックします。

2

Position が「Prominent」または「Inline」になっているか確認します。「Hide」になっていると画面にはボタンが表示されません。

3

一覧画面で行タップ時に Action を実行したい場合は、Views → 対象ビュー → Behavior → Event Actions → Row Selected に Action が割り当てられているか確認します。

🔴 Bot が発火しない（Audit history に履歴が出ない）
💡 原因

Bot が Disabled（無効） になっている／Event の条件式が TRUE にならない／Data change type が一致していない、などが原因です。

✅ 対処法
1

Automation → Bots で、対象 Bot の行の左にあるトグルが 緑（Enabled） になっているか確認します。

2

Event の Data change type が対象の操作と一致しているか確認します。例：承認ボタン（Update 操作）なら Updates only または Adds, Updates, or Deletes を含んでいる必要があります。

3

Condition 欄の式を Test します。意図したレコードで TRUE を返すか確認してください。

4

Scheduled Bot の場合、Bot の 「…」メニュー →「Test」 で手動テストできます（プロトタイプ状態でも実行可能）。

🔴 メールが送信されない（Audit には成功と出るのに届かない）
💡 原因

送信先アドレスの式が空文字を返している／迷惑メールフォルダに振り分けられている／無料プランの送信上限に達している、などの可能性があります。

✅ 対処法
1

Task の To 欄の式を確認し、対象レコードで実際のメールアドレスが返るか Test します（例：[社員ID].[メールアドレス]）。

2

送信先の 迷惑メール（スパム）フォルダ を確認します。初回は AppSheet からのメールがスパム判定されがちです。

3

無料プラン上限（1日あたり約10通）を超えていないか、Audit history のエラーメッセージで確認します。

🔴 同じメールが何度も届いてしまう
💡 原因

Event の Condition に 状態遷移の判定 が含まれておらず、レコードが更新されるたびに同じ条件が TRUE を返してしまっています。

✅ 対処法
1

Bot の Event Condition に、[_THISROW_BEFORE] を使った状態遷移判定を追加します。

2

例：単に [承認ステータス] = "承認済み" ではなく、次の式にします。

AND(
  [承認ステータス] = "承認済み",
  [_THISROW_BEFORE].[承認ステータス] <> "承認済み"
)

これで「承認済みに 変わった瞬間」にだけ発火します。

9-4 パフォーマンス改善の基本

データが増えてきたり、関数・Slice・Virtual Column が多くなってくると、アプリの Sync（同期）が遅くなったり、画面の表示がもたつくことがあります。ここでは中級レベルで実践できるパフォーマンス改善のポイントをまとめます。

■ 1. Virtual Column を増やしすぎない

Virtual Column は便利ですが、レコード表示のたびに再計算される ため、数が増えると Sync・画面遷移が遅くなります。以下を意識してください。

  • 表示時だけ必要な値は Virtual Column、常に保存が必要な値は通常カラムにする
  • 同じ式を使う Virtual Column が複数ある場合は、1つにまとめて他から参照する
  • 使われていない Virtual Column は削除する

■ 2. Slice の条件式を軽くする

Slice は Sync のたびに全レコードに対して評価されます。重い式（テーブルをまたぐ LOOKUP、SELECT を多用するなど）は避け、できるだけシンプルな比較で済むようにテーブル設計を調整してください。

■ 3. Updates allowed の最適化

Data → Tables → 各テーブルの Are updates allowed? で、実際にアプリ上で変更が必要な操作だけを有効にします。例えば「社員マスタ」はマスタデータのため、通常は Read-Only にしておくと安全かつ Sync も軽くなります。

テーブル推奨設定
社員マスタRead-Only（編集は管理者のみ、別アプリで運用する想定）
勤怠記録Adds, Updates（削除は不可にして履歴保全）
休暇申請Adds, Updates, Deletes

■ 4. 大量データには Security Filter（上級編）

レコード数が数百〜数千件を超えると、全データをアプリに読み込むのは非効率です。上級編で扱う Security Filter を使えば、ログインユーザーに応じて そのユーザーに関係する行だけをアプリにロード できます（例：自分の勤怠記録だけ表示）。大量データを扱うアプリの必須機能です。

💡 補足 ─ 現在のアプリのパフォーマンスを測る
Monitor → Performance Profile を開くと、Sync にかかった時間と、その内訳（テーブル別・ルール別）を可視化できます。ボトルネックを特定する際の出発点として活用してください。

9-5 アプリ公開（デプロイ）への道筋

ここまで作成してきたアプリは プロトタイプ状態 です。開発者本人は全機能を使えますが、他のユーザーに配布して本格運用するには デプロイ（Deploy） が必要です。

■ プロトタイプ状態とデプロイ済み状態の違い

比較項目プロトタイプ状態デプロイ済み状態
料金無料有料プラン必須
開発者（自分）の動作全機能利用可能全機能利用可能
他ユーザーの利用表示のみ（アプリ動作はするが警告表示あり）安定して利用可能
Automation 送信数1日約10通までプランに応じて大幅に拡大
外部連携・高度な機能制限あり制限解除

■ デプロイ前にチェックすること（Deployment Check）

AppSheet には、デプロイ前にアプリの設定をチェックしてくれる機能があります。

1

左メニューの Manage アイコン（⚙） をクリックし、Deploy を選択します。

2

Deployment Check セクションの 「Run deployment check」 をクリックします。

3

チェック結果が一覧表示されます。Error（赤） は必ず、Warning（黄） もできるだけ解消します。

■ よくある Deployment Check の指摘

指摘内容対応
Table には Key カラムが必要各テーブルのキーカラムを Data → Columns で指定
Image / File カラムが未設定画像や添付ファイルを格納する列の Type を正しく設定
Label が未設定少なくとも1カラムに Label を設定（通常は「氏名」などの表示用）
Initial value の式でエラー式の構文エラーを修正

■ ユーザーへの共有（概要）

デプロイ後は、Users → + Add users からメールアドレスを指定してユーザーを招待します。招待されたユーザーは、AppSheet アプリをスマートフォンにインストールして使えます。共有の詳細手順は上級編で扱います。

⚠️ 本マニュアルではデプロイは必須ではありません
中級編の学習はすべてプロトタイプ状態で完結します。本格的な業務運用を始める段階になったら、組織のライセンス管理者と相談してデプロイを検討してください。
